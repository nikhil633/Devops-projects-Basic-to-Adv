01 Core concepts

Five nouns cover almost everything in Docker's model. Get these solid and every command below is just a verb applied to one of them.

Image

A read-only template built from a Dockerfile — a stack of filesystem layers plus metadata (entrypoint, env, exposed ports). Images are immutable and content-addressed; every layer is cached and shared across images that share it.

Container

A running (or stopped) instance of an image: the image's layers plus one thin writable layer on top. Ephemeral by design — anything written to that top layer disappears when the container is removed unless it's in a volume or bind mount.

Layer

Each RUN, COPY, and ADD instruction produces a new layer. Layers are cached by content hash — reorder your Dockerfile so things that change rarely (dependency manifests) come before things that change often (source code) and you get real build-time savings.

Registry

Where images live: Docker Hub, GHCR, ACR, ECR, GCR. docker push/pull talk to a registry; tags (myapp:1.4.2) and digests (myapp@sha256:...) are how you address a specific image inside one.

Volume / Network

A volume is Docker-managed persistent storage that outlives any single container. A network is a virtual switch that lets containers find each other by name — every user-defined bridge network gets embedded DNS for free.

02 Image → container lifecycle

The path from source code to a running process, and the command that drives each hop.

→
docker build
produces an image
→

to a registry

In Kubernetes this same image is what a Pod's spec.containers[].image points at — everything you validate locally with docker run is the same artifact the kubelet will pull and start on a node.

03 Image commands

CommandWhat it does
docker build -t app:1.0 .Build an image from the Dockerfile in the current context, tagging it app:1.0
docker build -f Dockerfile.prod --target runtime -t app:1.0 .Build from a named file, stopping at a specific multi-stage target
docker build --build-arg NODE_ENV=production .Pass a build-time variable into ARG
docker imagesList local images
docker image ls -a --digestsList all images including intermediate ones, with content digests
docker pull nginx:1.27-alpineFetch an image (and specific tag) from a registry

docker tag app:1.0 myrepo/app:1.0Create an additional tag pointing at the same image
docker rmi app:1.0Remove an image (fails if a container still references it)
docker history app:1.0Show each layer, its size, and the instruction that created it
docker inspect app:1.0Full JSON metadata — env, entrypoint, exposed ports, layer digests

TIP

Always build with an explicit -t name:tag. An untagged build still works but leaves you hunting for a <none> image ID in docker images.

06 Volumes & networks

CommandWhat it does
docker volume create pgdataCreate a named, Docker-managed volume
docker volume lsList volumes
docker volume inspect pgdataShow the volume's mountpoint on the host
docker volume rm pgdataDelete a volume (must be unattached)
docker network create app-netCreate a user-defined bridge network with built-in DNS

TIP

Always create a user-defined network rather than relying on the default bridge — the default bridge has no built-in DNS, so containers can only reach each other by IP.

07 System & cleanup

CommandWhat it does

08 Docker Compose

Compose describes a multi-container application declaratively — the closest thing to a Kubernetes manifest for local development.

CommandWhat it does
docker compose up -dBuild (if needed) and start every service, detached
docker compose up -d --buildForce a rebuild before starting
docker compose downStop and remove containers, networks (keeps named volumes)
docker compose down -vAlso remove named volumes — full reset
docker compose psStatus of services defined in this compose project
docker compose logs -f apiTail logs for one service
docker compose exec api shShell into a running service
docker compose configRender the final merged config — great for debugging env interpolation

Example: app + database

docker-compose.yml 
services:
  api:
    build:
      context: .
      target: runtime
    image: myapp:local
    ports:
      - "8080:8080"
    environment:
      DATABASE_URL: postgres://app:app@db:5432/appdb
    depends_on:
      db:
        condition: service_healthy
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://localhost:8080/health"]
      interval: 10s
      timeout: 3s
      retries: 5

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: app
      POSTGRES_DB: appdb
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app"]
      interval: 5s
      retries: 5

volumes:
  pgdata:

09 Dockerfile instruction reference

InstructionWhat it does
FROMBase image for the stage — the only instruction that can start a new stage
ARGBuild-time-only variable, not present in the final image or a running container
RUNExecutes a command and commits the filesystem result as a new layer
COPYCopy files from the build context (or another stage with --from) into the image
ADDLike COPY, plus remote URL fetch and auto-extraction of tarballs — prefer COPY unless you need those
WORKDIRSets (and creates) the working directory for subsequent instructions
ENVEnvironment variable baked into the image and every container run from it
EXPOSEDocuments the port the app listens on — does not publish it; -p at runtime does that
USERSwitches the effective user for subsequent instructions and the running container
VOLUMEDeclares a mount point Docker should treat as external state
LABELKey/value metadata — owner, source repo, version — queryable via docker inspect
HEALTHCHECKCommand Docker runs periodically to decide if the container is "healthy"
CMDDefault command for the container — overridden by args passed to docker run
ENTRYPOINTFixed executable for the container; CMD then supplies its default arguments
SHELLOverrides the default shell used for the shell form of RUN/CMD/ENTRYPOINT
ONBUILDRegisters an instruction to run later, when this image is used as a base for another build
STOPSIGNALOverrides the signal sent by docker stop (default SIGTERM)
TIP

CMD vs ENTRYPOINT: use ENTRYPOINT ["node","server.js"] when the container should always run that binary, and reserve CMD for default arguments the caller might reasonably override.

10 Multi-stage builds

A single Dockerfile can contain several FROM blocks, each one a named stage. Later stages can COPY --from=<stage> specific artifacts out of earlier ones — compiler, build tools, and source code never make it into the image you actually ship.

FROM node AS deps
install packages
→
FROM node AS build
compile / bundle
→
FROM distroless AS runtime
copy artifact only

The payoff is size and attack surface: a Go binary built in a 900MB toolchain image can ship in a scratch or distroless image under 20MB, with no shell, no package manager, no compiler for an attacker to abuse if they land inside the container.

TIP

Stop a build at an intermediate stage for local debugging with docker build --target build -t app:debug . — useful when the final stage is a minimal image with no shell to exec into.

11 Production-grade multi-stage Dockerfiles

Three stacks, same discipline throughout: pinned base image digests where it matters, dependency install cached separately from source, a non-root user, and a HEALTHCHECK. Adjust ports/paths to your app.

Dockerfile — Node.js / Express, npm build 
# ---- Stage 1: install deps with full lockfile fidelity ----
FROM node:20.17-alpine3.20 AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci --omit=dev --ignore-scripts

# ---- Stage 2: build (needs devDependencies) ----
FROM node:20.17-alpine3.20 AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci --ignore-scripts
COPY . .
RUN npm run build

# ---- Stage 3: minimal runtime ----
FROM node:20.17-alpine3.20 AS runtime
ENV NODE_ENV=production
WORKDIR /app

# non-root user (alpine node images ship a "node" user, uid 1000)
RUN apk add --no-cache dumb-init
COPY --from=deps    /app/node_modules ./node_modules
COPY --from=build    /app/dist          ./dist
COPY package.json .

USER node
EXPOSE 8080

HEALTHCHECK --interval=30s --timeout=3s --start-period=5s --retries=3 \
  CMD node -e "require('http').get('http://localhost:8080/health',r=>process.exit(r.statusCode===200?0:1))"

ENTRYPOINT ["dumb-init", "--"]
CMD ["node", "dist/server.js"]
TIP

dumb-init as PID 1 fixes zombie-process reaping and correct signal forwarding — Node itself doesn't handle SIGTERM/SIGCHLD as PID 1 gracefully.

Dockerfile — Python / FastAPI, uv or pip, venv copied across stages 
# ---- Stage 1: build a self-contained virtualenv ----
FROM python:3.12-slim AS build
ENV PYTHONDONTWRITEBYTECODE=1 PYTHONUNBUFFERED=1
WORKDIR /app

# build deps only exist in this stage, never in runtime
RUN apt-get update && apt-get install -y --no-install-recommends \
      build-essential \
    && rm -rf /var/lib/apt/lists/*

RUN python -m venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

# ---- Stage 2: slim runtime, venv copied in wholesale ----
FROM python:3.12-slim AS runtime
ENV PYTHONDONTWRITEBYTECODE=1 PYTHONUNBUFFERED=1 \
    PATH="/opt/venv/bin:$PATH"
WORKDIR /app

RUN groupadd -r app && useradd -r -g app -d /app app
COPY --from=build /opt/venv /opt/venv
COPY --from=build --chown=app:app /app .

USER app
EXPOSE 8000

HEALTHCHECK --interval=30s --timeout=3s --start-period=5s --retries=3 \
  CMD python -c "import urllib.request,sys; sys.exit(0 if urllib.request.urlopen('http://localhost:8000/health').status==200 else 1)"

CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
TIP

Copying the whole /opt/venv across stages avoids reinstalling build-essential in the runtime image — compiled wheels come along for free, gcc doesn't.

Dockerfile — Go, static binary into a distroless runtime 
# ---- Stage 1: build a fully static binary ----
FROM golang:1.23-alpine AS build
WORKDIR /src

# cache module downloads separately from source changes
COPY go.mod go.sum ./
RUN go mod download

COPY . .
RUN CGO_ENABLED=0 GOOS=linux GOARCH=amd64 \
    go build -ldflags="-s -w" -o /out/server ./cmd/server

# ---- Stage 2: distroless — no shell, no package manager ----
FROM gcr.io/distroless/static-debian12:nonroot AS runtime
WORKDIR /app
COPY --from=build /out/server .

# distroless "nonroot" image already runs as uid 65532
USER nonroot:nonroot
EXPOSE 8080

ENTRYPOINT ["/app/server"]
CAUTION

Distroless has no shell, so HEALTHCHECK CMD and docker exec ... sh won't work here. Build health checks into the app itself and rely on your orchestrator's (k8s) HTTP liveness/readiness probes instead.

12 .dockerignore

Excluded paths never enter the build context, which means faster docker build uploads, smaller layer-cache invalidation surface, and no accidental secrets baked into an image.

.dockerignore 
# VCS & CI
.git
.github

# dependencies (reinstalled inside the build)
node_modules
__pycache__
*.pyc
.venv

# local env & secrets — never let these into an image
.env
.env.*
*.pem
*.key

# build artifacts / editor / OS noise
dist
build
*.log
.DS_Store
.vscode
.idea

# tests & docs — usually not needed in the runtime image
tests
docs
README.md

13 Production hardening checklist

  • Pin base image tags (and digests for anything security-sensitive) — never build FROM node:latest in CI
  • Run as a non-root USER — most CIS/Pod Security Standard scanners fail a build without one
  • Order instructions so dependency manifests are copied and installed before the rest of the source, to preserve layer cache
  • Use multi-stage builds so compilers, dev dependencies, and source never reach the final image
  • Prefer a minimal base — alpine, slim, or distroless — over a full OS image
  • Add a .dockerignore before the first build, not after a secret leaks into a layer
  • Set explicit resource-aware defaults; let Kubernetes requests/limits be the real ceiling in a cluster
  • Add a HEALTHCHECK (or, in k8s, liveness/readiness probes) instead of assuming "running" means "ready"
  • Scan images in CI — docker scout, Trivy, or Grype — before they ever reach a registry
  • Sign and generate an SBOM for anything that ships to production (docker buildx build --sbom=true --provenance=true)
  • Never bake secrets in with ENV or ARG — use BuildKit's --secret mount or inject at runtime
BuildKit secret mount — no secret in any layer, ever 
# Dockerfile
RUN --mount=type=secret,id=npmrc,target=/root/.npmrc \
    npm ci --omit=dev

# build command
docker build --secret id=npmrc,src=$HOME/.npmrc -t app .

14 Buildx, cache & multi-arch

Modern Docker builds run on BuildKit by default; buildx is the CLI front-end for its extra capabilities — remote cache, multi-platform output, SBOM/provenance attestations.

CommandWhat it does
docker buildx create --useCreate and switch to a new builder instance (needed for multi-platform builds)
docker buildx build --platform linux/amd64,linux/arm64 -t app:1.0 --push .Build and push one manifest covering both architectures — essential if your nodes mix Graviton/ARM and amd64
docker buildx build --cache-to=type=registry,ref=myrepo/app:cache --cache-from=type=registry,ref=myrepo/app:cache .Persist layer cache in a registry so CI runners share it across jobs
docker buildx bakeBuild several related targets/platforms from one declarative docker-bake.hcl file
docker buildx build --sbom=true --provenance=true .Attach a software bill of materials and build provenance attestation to the image
TIP

In GitHub Actions, pair docker/setup-buildx-action with cache-from: type=gha / cache-to: type=gha,mode=max — no registry round-trip needed for cache.
